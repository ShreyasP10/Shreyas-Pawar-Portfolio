2d • 


⟡ I thought building a real-time chat application would mostly be a frontend project.

But I was wrong.

The moment Mahajan Atharva and I decided that every message should be encrypted before it reached the database, almost every feature had to be redesigned.

Replies.

Read receipts.

File sharing.

Message reactions.

Voice calls.

None of them were particularly difficult on their own.

The real challenge was making them all work without the server ever understanding the message content.

That's how Chatrixz slowly stopped being "just another chat app" and became one of the most technically challenging projects I've worked on.


⟡ One architectural decision changed everything

Most messaging platforms allow the backend to understand message contents.

We deliberately chose a different approach.

Messages are encrypted on the client using AES-256-GCM before they're uploaded.

Firestore stores only ciphertext—not plain text.

At first, that sounded like a small design decision.

It wasn't.

Once the server could no longer understand message contents, features that normally feel straightforward suddenly became architectural problems.

How should replies work?

How should metadata be handled?

What belongs on the client?

What belongs on the server?

Those questions shaped almost every part of the application.


⟡ What Chatrixz became

Instead of simply building a messaging platform, we ended up exploring several areas of modern web development.

› Client-side Cryptography

› Real-time Synchronization

› WebRTC Peer-to-Peer Communication

› Progressive Web Apps (PWA)

› Browser Storage & Offline Support

› Modern Frontend Architecture

Looking back, the biggest lesson wasn't about React or Firebase.

It was learning how one architectural decision can influence an entire system.

A huge thanks to Mahajan Atharva for building this project with me. Looking forward to building even more together.


⟡ I'd Love Your Perspective

If you were designing an encrypted messaging platform today,

would you accept additional architectural complexity to ensure the server never sees a single plain-text message?

Or would you choose a simpler architecture that gives the backend more responsibility?

What would you give up for stronger privacy?

Server-side search?

Simpler debugging?

Faster development?

I'd love to hear your thoughts.

⟡ What if we could extract more detail from thermal satellite imagery without launching a new satellite?
That's the idea behind Kepler-404, a prototype I built for the ISRO Space Applications Centre (SAC) – BAH 2026 Hackathon.
Landsat 9 Thermal Infrared (TIR) imagery plays an important role in applications such as urban heat island analysis, wildfire monitoring, volcanic activity observation, and environmental research. However, its 200m spatial resolution can limit detailed analysis.
Instead of treating this as just an image processing problem, I wanted to explore how an AI-powered workflow could enhance thermal imagery while preserving the geospatial information required for real-world GIS applications.

⟡ What Kepler-404 demonstrates
› Super-resolves Landsat 9 Thermal Infrared imagery from 200m → 100m
› Colorizes grayscale thermal imagery into physically consistent RGB visualizations
› Preserves CRS and affine transformations for compatibility with GIS platforms like QGIS and ArcGIS
› Provides an interactive web interface with before/after comparison and GeoTIFF export

⟡ Tech Stack
› Python & Flask
› PyTorch
› OpenCV
› Rasterio & GDAL
› NumPy
› HTML • CSS • JavaScript
› Designed to support ESRGAN, SwinIR, Pix2Pix, and Diffusion Models

⟡ Current Status
Kepler-404 is currently a prototype that validates the complete end-to-end workflow using a mock inference layer.
The objective was to build a modular foundation that allows production-ready AI models to be integrated without redesigning the frontend or backend architecture.
Working on this project gave me a deeper appreciation for the intersection of AI, Computer Vision, Remote Sensing, and Geospatial Computing. There's still plenty to improve, and I'm looking forward to continuing its development.

CropIQ – Crop Disease Identifier Application

Maharashtra State Board of Technical Education (MSBTE)

Mar 2025 · 1 mo

I participated in the MSBTE State Level Project Competition 2025 (Mumbai Region) held in March 2025, representing Muchhala Polytechnic, Thane. During the competition, I presented my project titled CropIQ – Crop Disease Identifier Application at Shivajirao S. Jondhle Polytechnic, Asangaon.

CropIQ is an AI-powered Android application designed to detect diseases in various crops such as apple, banana, and others using Computer Vision and Deep Learning. The application is developed using Java and Kotlin, with a Convolutional Neural Network (CNN) implemented through TensorFlow to analyze crop images and accurately identify diseases. In addition to detection, the app also provides recommended solutions and preventive measures for each identified disease, helping users take timely and informed action. Firebase is used for backend services including data storage and application management.

The project focuses on early disease detection and actionable guidance, helping farmers and agricultural stakeholders reduce crop losses and improve productivity. Participating in this state-level competition provided valuable exposure, expert feedback, and peer learning, and marks a key milestone in my journey from an IT Diploma student to pursuing B.Tech in Computer Engineering, motivating me to continue building impactful, real-world AI-driven solutions.
